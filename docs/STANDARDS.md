# Sous and open standards

Sous's native formats (PROTOCOL.md) are the source of truth: the gateway signs them, the rules engine reads them and the audit log records them. This page maps each object onto the open standards an outside agent or auditor already knows. It lists what we implement natively, what we export as a view, and what is still missing.

Every export is built from the **signature-verified** native payload, never from the stored copy. A tampered mandate, quote or receipt gives `409 *_signature` instead of an export. Exports are deterministic: the same object gives byte-identical output, because Ed25519 signatures and our canonical JSON are deterministic. Code: [`sous/standards.py`](../sous/standards.py). Tests: [`tests/test_standards.py`](../tests/test_standards.py), offline, validating against the AP2 JSON Schemas vendored in `tests/fixtures/ap2/`.

| **Mandate** (`sous-mandate+jws`; optional buyer `vc+jwt`) | AP2 v0.2 **open checkout mandate** + **open payment mandate** (v0.1: IntentMandate); W3C VC 2.0 | JWS (RFC 7515, EdDSA) by the gateway. ## Peppol BIS Ordering 3.0 (UBL 2.1 XML)

Peppol is the EU e-procurement network; in Finland it carries most B2B and public-sector e-invoices and, increasingly, orders. A Peppol access point (or an ERP's EDI layer) can take Sous's orders without knowing Sous's JSON.

- `GET /orders/{id}/peppol` (default `doc=order`): a Peppol BIS **Order** for an `ordered` order. Other statuses give `409 peppol_not_ordered`: a held, refused or rejected order was never placed with the seller.
- `GET /orders/{id}/peppol?doc=order_response`: an **Order Response**. `AP` (accepted) for `ordered`; `RE` (rejected) for refused / rejected / expired orders, with the reason in `Note`; `CA` (accepted with change) once Valio Aimo's signed amendments ([sous/amendments.py](../sous/amendments.py): short pick, delay, substitution at pick, cancelled line) have changed lines. CA lists only the changed lines, as they now stand: `LineStatusCode` 3 (changed; substitutions and short picks say so in the line `Note`) or 7 (not accepted: cancelled, quantity 0), with the promised delivery date. Amendments still waiting for the buyer change nothing yet. `409 peppol_not_final` while an order is held for approval.
- The Order always shows what the buyer ordered (the signed quote's orderable lines), also after amendments; its receipt reference is the current, re-signed receipt.
- Read scoping is the same as `GET /orders/{id}` (private orders answer 404). Media type `application/xml`. Built from the signature-verified receipt and quote, deterministic. Code: `peppol_order`, `peppol_order_response` in [`sous/standards.py`](../sous/standards.py); tests: [`tests/test_peppol.py`](../tests/test_peppol.py).

**Limits.**
- **Participant ids are placeholders.** Peppol needs `EndpointID`s from the EAS list (0216 = Finnish OVT code, 0037 = business id). Sous's customer master has no Peppol ids, so both parties carry a labelled `PLACEHOLDER-…` value under scheme 0216 until Valio Aimo's master data supplies them. A real access point would reject these.
- **Validated structurally, not by schematron.** Tests check that the XML is well-formed, has the elements BIS marks mandatory, writes the top-level elements in UBL 2.1 sequence order, uses EUR on every amount and that line amounts sum to the order totals. The UBL 2.1 XSDs (the Order schema pulls in the large common-component schemas) are not vendored and there is no XML Schema validator in our dependencies. Next step: run the OpenPeppol validation artefacts (UBL XSD + PEPPOL-T01/T76 schematron) in CI, e.g. with phive.
- **List prices.** As in the ORDERS05 outbox, prices are the list prices Sous quoted; the seller's ERP prices with the customer's conditions.
- **Substitutions in the Order Response** are shown as a changed line carrying the substitute item, with the original in `Note`, not with UBL's `SellerSubstitutedLineItem`.
- **Postal addresses** carry only the country (FI): Sous does not hold delivery addresses.

## Why not just adopt X?

- **Why not make AP2 the native format?** AP2 v0.2 is five months old and its object model has already been renamed once. Its mandates constrain *which items* and *how much money*. Our buyers' real constraints are allergens (unknown counts as unsafe), required claims, substitutions, cut-offs, delivery reliability and four tiers of human involvement. None of these has an AP2 constraint type. Keeping a small native format and *exporting* AP2 lets us follow AP2 as it changes without migrating signed history. The exports are tested against AP2's own published schemas, so the mapping can be checked.
- **Why not ACP?** ACP is a stateful checkout API between an AI platform and a merchant, centred on delegated card payment (Stripe Shared Payment Token). Valio Aimo customers buy on account, and the buyer side needs a policy layer that ACP leaves to the platform. Our quote → order lifecycle matches ACP's session → complete, so an ACP adapter is a thin facade (next steps).
- **Why not SD-JWT VCs (as AP2 uses) instead of `vc+jwt`?** Selective disclosure hides fields from the merchant. In Sous the gateway *is* the merchant side and must see the whole mandate to enforce it. `vc+jwt` (VC 2.0 + JOSE) is the W3C Recommendation, verifies with any JOSE library and reuses our JWS code. Moving to SD-JWT is mechanical once a buyer wants to hide parts of a mandate from a third party.
- **Why not JSON-LD Data Integrity proofs?** They need RDF canonicalisation, which adds a dependency and an attack surface for no gain over JOSE here (DECISIONS.md 10).
- **Why Ed25519 and not ES256 everywhere?** Small keys, deterministic signatures, and the same algorithm for every gateway object. Buyers may sign with ES256 because that is what passkeys and WebCrypto offer.
- **Why MCP and OpenAPI rather than A2A?** Today's buyer agents call tools. Sous is a tool provider (a gateway), not a peer agent that negotiates in tasks. A2A's agent card is still the best-known discovery document, so we publish one that points at our real interfaces.
- **Why not x402?** x402 settles per-request payments in stablecoins over HTTP 402. Food-service wholesale settles monthly by invoice under credit terms, so x402 matters for the payment step only if Valio Aimo ever wants pay-per-order settlement.

## Next steps to production (honest)

1. **Agent keys and key binding.** Replace bearer tokens with an agent key pair (DPoP, RFC 9449, or mTLS) so `cnf` carries a real JWK. Then the buyer can sign the AP2 open mandates as SD-JWTs, and the agent can present them with a key-binding JWT.
2. **Line-item constraints.** For standing orders, the mandate could list the acceptable SKUs, which is AP2's `checkout.line_items`. That makes the open checkout mandate fully schema-valid for that case.
3. **Accept AP2 inbound,** not only export: `POST /orders` with a closed checkout mandate (SD-JWT + KB-JWT) that references our `checkout_hash`, verified the same way as the buyer VC.
4. **An ACP facade:** `POST /checkout_sessions` → quote, `POST /checkout_sessions/{id}/complete` → order, using the ACP 2026-04-17 OpenAPI.
5. **Key rotation and signed cards:** several keys in the JWKS with KMS-held private keys, and JWS signatures on the agent card (RFC 8785 canonical JSON, as A2A specifies).
6. **Revocation:** a W3C Bitstring Status List for mandates, so revocation is checkable without asking the gateway.
7. **Audit anchoring:** publish signed chain heads to the buyer or to a transparency log, with inclusion proofs.
8. **Peppol in production:** real Peppol participant ids from the customer master, an access point (or Valio's EDI operator) as the transport, and `SellerSubstitutedLineItem` for substitutions at pick.
9. **Spec drift:** AP2, A2A and MCP server cards all changed in 2026. CI should re-download their schemas and run `tests/test_standards.py` against the latest versions, not only the pinned ones.
